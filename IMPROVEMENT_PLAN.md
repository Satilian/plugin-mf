# План доработок plugin-mf для 100+ микрофронтендов

Приоритеты: P0 — корректность; P1 — устойчивость и воспроизводимость; P2 — производительность и управление.
Каждый подпункт рассчитан на отдельную небольшую задачу или PR. Проверки конкретного поведения добавляются вместе с изменением.

## P0.1. Согласованность релизов server/client/types

**Необходимость:** SSR может использовать старый серверный компонент, а браузер — новый клиентский. При независимых деплоях это вызывает ошибки гидрации и несовместимость контрактов.

- [x] Добавить `releaseId` и версию формата манифеста, предусмотреть переход со старого формата.
- [x] Создавать общий манифест релиза со ссылками на server, client и types.
- [x] Размещать артефакты по неизменяемому пути `/mf/<releaseId>/`.
- [x] Публиковать указатель текущего релиза после загрузки всех артефактов.
- [x] Фиксировать выбранные версии remotes на время SSR-запроса.
- [x] Передавать карту выбранных релизов в HTML для браузерной загрузки.
- [x] Определить обновление указателя и срок хранения старых релизов для открытых страниц и rollback.

**Критерий готовности:** деплой во время SSR не приводит к смешиванию версий; открытая страница работает после нового релиза.

## P0.2. Надёжность серверного загрузчика

**Необходимость:** кеш по имени файла может смешивать разные providers. Неатомарная запись опасна при конкурентных загрузках, а загрузка только entry не поддерживает дополнительные серверные chunks.

- [x] Формировать ключ кеша из provider, releaseId и полного URL; проверять границы пути кеша.
- [x] Сделать директорию кеша настраиваемой и проверять доступность записи.
- [x] Записывать через временный файл и атомарное переименование.
- [x] Защитить общий кеш от гонок нескольких процессов.
- [x] Добавить серверные chunks и assets в манифест.
- [x] Скачивать необходимые файлы с сохранением структуры каталогов.
- [x] Разделить очистку дискового кеша и смену исполняемой версии: удаление файлов не очищает ESM-кеш Node.
- [x] Добавить удаление устаревших релизов с ограничением размера кеша и защитой активных загрузок.

**Критерий готовности:** одинаковые имена файлов разных providers не конфликтуют; конкурентная загрузка и серверный dynamic import работают.

## P1.1. Ограничение времени загрузки и обработка отказов

**Необходимость:** недоступный микрофронтенд должен влиять на ограниченную область страницы, а время ожидания должно быть предсказуемым.

- [x] Ввести структурированные ошибки с remote, releaseId и этапом загрузки.
- [x] Добавить настраиваемые таймауты для манифестов, модулей и типов.
- [x] Добавить ограниченные повторы временных сетевых ошибок с общим бюджетом времени.
- [x] Реализовать повторную попытку после неуспешной загрузки `React.lazy` и дедупликацию попыток.
- [x] Подготовить пример локального Error Boundary, Suspense и fallback для браузера и SSR.
- [x] Добавить deadline и abort SSR в consumer.
- [x] Добавить circuit breaker для providers с повторяющимися отказами.

**Критерий готовности:** отказ одного remote не блокирует остальные; ожидание ограничено; после восстановления provider компонент можно загрузить повторно.

## P1.2. Кеширование и воспроизводимость типов

**Необходимость:** сейчас сборка обращается ко всем providers, удаляет предыдущие типы и при ошибке подменяет контракт на `any`.

- [x] Добавить режимы синхронизации `strict`, `best-effort`, `off`.
- [x] Сохранять последнюю успешную версию типов и явно сообщать о её использовании.
- [x] Обновлять кеш атомарно после полной загрузки и проверки.
- [x] Привязать декларации к `releaseId`.
- [x] Добавить lock-файл выбранных релизов.
- [x] Пропускать загрузку уже закешированных версий.
- [x] Ограничить общую параллельность сетевых запросов.
- [x] Разрешить явный выбор remotes для синхронизации.
- [x] Вынести синхронизацию в отдельную команду с поддержкой offline-сборки.

**Критерий готовности:** повторная сборка не скачивает неизменившиеся типы; CI использует фиксированные контракты; потеря типизации явно видна.

## P1.3. Совместимость shared-зависимостей

**Необходимость:** при большом количестве команд возникают разные версии React и общих библиотек. Текущий registry не проверяет их совместимость.

- [x] Расширить конфигурацию параметрами `version`, `requiredVersion`, `singleton`.
- [x] Сохранить поддержку сокращённой записи строками.
- [x] Регистрировать реальные версии зависимостей host.
- [x] Записывать требования provider в манифест.
- [x] Проверять совместимость до исполнения remote.
- [x] Определить правила subpath imports, включая `react/jsx-runtime`.
- [x] Добавить аналогичные проверки серверных externals.

**Критерий готовности:** несовместимая зависимость обнаруживается до рендера с понятной диагностикой.

## P1.4. Совместимость с CSP и контроль источников

**Необходимость:** браузерный `new Function` мешает работе под строгой CSP. Серверный загрузчик исполняет скачанный код внутри процесса host.

- [x] Заменить браузерный `new Function` на динамический import с подходящей настройкой сборки.
- [x] Добавить проверку разрешённых протоколов и origins.
- [x] Проверять адреса assets и конечные URL после redirects.
- [x] Добавить хеши серверных файлов в манифест и проверять перед импортом; учитывать, что это не защищает от подмены самого манифеста.
- [x] Документировать модель доверия и требования к публикации артефактов.

**Критерий готовности:** загрузка работает без `unsafe-eval`; неожиданные источники и повреждённые файлы отклоняются.

- [x] Связывать SSR-события с идентификатором запроса, не сохраняя контекст глобально.
- [x] Добавить метрики ошибок, повторов, загрузок и дискового кеша.
- [x] Подготовить пример подключения логирования и tracing.

**Критерий готовности:** по конкретному запросу можно определить выбранные релизы и причину задержки.

## P2.2. Размер bundles и скорость загрузки

**Необходимость:** отключённый `splitChunks` может дублировать код между exposes. Оптимизации нужно подтверждать на реальных маршрутах.

- [x] Снять исходные показатели холодной и повторной загрузки до оптимизаций.
- [x] Добавить отчёт о повторяющихся зависимостях.
- [x] Поддержать общие chunks внутри provider после доработки формата assets и загрузчиков.
- [x] Добавить preload для remotes конкретного маршрута.
- [x] Ограничить параллельность preload.
- [x] Ввести бюджеты JS/CSS и количества активных remotes на маршрут.

**Критерий готовности:** размер ресурсов и задержки уменьшаются; preload загружает только необходимые микрофронтенды.

## P2.3. Runtime registry и управление релизами

**Необходимость:** встроенные в bundle адреса затрудняют rollback, canary и отключение remote без пересборки consumer.

- [ ] Отделить registry от загрузчика, сохранив статическую конфигурацию.
- [ ] Добавить внешний registry с валидацией и кешем.
- [ ] Сохранять последнюю успешную конфигурацию.
- [ ] Добавить выбор конкретного релиза и отключение remote.
- [ ] Применять обновления к новым запросам, сохраняя версии начатого SSR.
- [ ] Добавить стабильный canary-выбор для пользователя или сессии и передавать выбор браузеру.
- [ ] Проверить rollback без пересборки host.

**Критерий готовности:** переключение релиза не смешивает версии внутри страницы.

## P2.4. Проверка масштаба и длительной работы

**Необходимость:** 100 зарегистрированных remotes и 100 одновременно используемых — разные нагрузки. Нужны воспроизводимые сценарии.

- [ ] Создать генератор тестовых providers.
- [ ] Проверить 100+ зарегистрированных remotes с разным количеством активных на странице.
- [ ] Проверить холодный старт и конкурентный SSR.
- [ ] Проверить несколько процессов с общим кешем.
- [ ] Проверить деплой и rollback во время запросов.
- [ ] Проверить медленные providers, 404, повреждённые артефакты и несовместимые shared-версии.
- [ ] Проверить расход памяти и диска при последовательных обновлениях.

**Критерий готовности:** установлены допустимые задержки и ресурсы, а поведение при сбоях предсказуемо.

## Начальная последовательность PR

1. Формат манифеста релиза.
2. Разделение SSR-кеша по provider и URL с учётом релиза.
3. Атомарная запись файлов.
4. Таймауты и структурированные ошибки.

Далее завершить согласованность SSR и браузера, поддержку серверных chunks и задачи P1. Поддержка chunks предшествует включению splitChunks; согласованность релизов предшествует canary и runtime-переключениям. Исходные нагрузочные показатели снять до оптимизаций.
